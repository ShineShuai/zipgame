# Difficulty tools

All tools read the SAME label files, both stored in git:
- `tools/ratings.json` — `[{ "key": puzzle text, "human": 2.75, "lo": 2, "hi": 3, "unsure": true? }]`. `lo`/`hi` = the range you stated,
  `human` = the number a model is fitted to (the midpoint, moved halfway toward the end you said it was "close to"), `unsure` = only
  written when true; a fit counts such a rating at weight 0.5 (`UNSURE_WEIGHT` in `src/core/ratings-io.js`).
- `tools/pairs.json` — `[{ "a": key, "b": key, "cmp": "harder" | "easier" | "same" }]`, `cmp` describes B relative to A
  ("this puzzle is harder than the previous one"). Pairs do not depend on what a "2" meant on the day, and are scored by RANKING accuracy.

Formats live in `src/core/ratings-io.js` and `src/core/pairs-io.js`. The design app's **Export / Import ratings.json** and
**Export / Import pairs.json** buttons (under "Correlation with your ratings") read and write exactly these files.

## Writing ratings in difficulty_rate.txt
A comment line BEFORE each puzzle block. Preferred form (parts in any order):

    human 2, range 2-3
    human 2.5, range 2-3, unsure
    range 3-5            (human = the midpoint, 4)
    human 4              (an exact rating)

Older forms are still read, with the same numbers as before: `this is 2`, `this is 2 or 3` (2.5), `this is 2 or 3, close to 3` (2.75),
`this is at least 3, close to 4 or 4` (human 4, range 3-5), `this is at least 4` (human 4, range 4-5), `this is at most 1` (human 0.5,
range 0-1), plus chatter such as `you graded as 3`, `not 4`, `instead of 3`. Anything else is an error, never a guess.

## Tools
| tool | what it does |
|---|---|
| `parse-ratings.mjs` | `difficulty_rate.txt` -> ratings JSON. Only NEW puzzles are read; **duplicates are reported, never skipped silently** (see below); `--check-labels` lists old comments whose parsed rating differs from the JSON. |
| `check-ratings.mjs` | Validates `ratings.json` and `pairs.json`: bad rows, exact duplicates (error), equivalent puzzles (warning, drawn as ASCII with their ratings), pairs that contradict your ratings. Exit 1 on errors. `npm test` runs it too. |
| `metrics-eval.mjs` | **Compare everything.** Per metric Spearman rho + bootstrap CI + rho after removing size; whole grading models under leave-one-out, a chronological holdout, the ladder grade's own constants, and (Part 5) **ranking accuracy** on pairs implied by your ratings and on `pairs.json`. Start here after adding labels. `--cap N` sets the reference-solve node cap (default 1e6; the app's own 9000 hides 15 of the rated puzzles). |
| `share-decode.mjs` | Decode a play-app share link (`?s=` code, or the whole link) to JSON: kind, size, grade, time, percent, strip, date, and the local seed. `--encode '<json>'` builds a code to craft test links. |
| `fit-trap.mjs` | Refit the trap grade: weighted ridge over trapMax, trapTop3, altFrac, lTr, then the cutpoints between grades (`--write` rewrites the `<TRAP_MODEL>` block in `src/core/trap.js`; unsure ratings count 0.5). `--cuts anchors` (default: only the 0\|1 and 3\|4 boundaries are fitted, the rest evenly spaced) / `fit` (all five) / `round` (old rule); `--anchor-weight 3` (ratings <= 0.5 or >= 3.5 count 3x in the cut fit); `--features`, `--lambda`, `--ladder-work-cap` (exploring only), `--cap N`. Prints leave-one-out rho / MAE and how many easy / hard anchor ratings get the right badge. |
| `size-level.mjs` | How much does the grid size change difficulty? Reads the real players' Game-of-Day times from the backends (`/stats`, or saved replies with `--stats reply.json`, repeatable) and the plain puzzle files (`--puzzles DIR`, default `../demo/GameOfDay`; their `# play_time_s` comment is the author's own time, one extra noisy observation, `--no-author` leaves it out). Excluded: the synthetic seed players, and on puzzles that need thinking (larger than 6x6 or grade >= 1) every play below the drawing floor of 0.5 s per cell (replays, plays without thinking); a day needs `--min-players 20` valid players. Fits `ln(median time) = alpha + gamma*ln(N^2/49) + c*(h-1.5) + level(N)` (`gotd-model.js fitTimeSize`; `--size-sd` = how far a size may deviate from the trend) and prints gamma, c, the size shift s(n) in grades, the per-size level and the global difficulty of local grades 0..5 (`--out FILE` writes JSON). Without valid days everything stays at the prior. `gotd-data.mjs` holds the shared loading. |
| `target-eval.mjs` | Does the targeted generator (design app, "🎯 Generate target grade"; `src/core/gen/target.js`) still reach every grade? Per size and target grade: hit rate, tried changes, seconds. `--sizes 6,7,8,9 --grades 0,1,2,3,4,5 --seeds 8 --effort 1 --retries 4 --no-minimize`; `--min-hit R` exits 1 when a (size, grade) hit rate is below R; `--independent` also checks that puzzles aimed at higher grades are harder by metrics the search never saw (guess points per cell, backtrack overhead, ladder grade) and prints their rank correlation with the target grade. Run after every refit. |
| `playlog-eval.mjs` | Correlates every metric and the Play badge with what players did (`playlog.json` from the play app: hold V, click "play log"): size-adjusted solve time, cells drawn and taken back. An objective label that grows with every puzzle played. |
| `behaviour.mjs` | The owner's side of the anonymous behaviour rows that the play app uploads (see `server/README.md`, "Behaviour rows"): `export` reads both backends into one file (puzzle as plain text, kind, skill, times, cells taken back), `delete` removes the rows of a puzzle / Game of Day / day / ids that the analysis found unuseful, `migrate` adds a column to the tables. |
| `ladder-eval.mjs` | Ladder details per rated puzzle (hardest level, passes per level, ms) and `--gen` soundness/timing check on generated puzzles. |
| `weighted.mjs` | Exploratory composites of ladder outputs vs the ratings. |
| `features.mjs` | Library: every metric of a puzzle in one object (`featuresOf`), shared by `metrics-eval`, `gotd-fit` and `gotd-seed`. |
| `gotd-fit.mjs` | Fits every metric / grade to `ratings.json` and ranks them -> `tools/gotd-models.json` (see below). |
| `gen-target.mjs` | CLI around the targeted generator, for scripts and GitHub Actions: `--size N --grade G [--max-walls W] [--min-checkpoints K] [--max-checkpoints K] [--retries R] [--effort X] [--seed S --count C] [--out DIR] [--no-minimize] [--allow-miss] [--json] [--time]`. Without `--retries` it searches until the grade is met. Counts only, no clock: the same arguments give the same puzzle file (`--time` adds the search time to the file's comments, which breaks that). Writes `zip-<n>x<n>-g<grade>-s<seed>.txt` per puzzle or prints / JSON-lines them; exit 2 = target missed. |
| `gotd-seed.mjs` | Seeds a Game of Day with 3..8 synthetic players on every configured backend (see below). |
| `print-bin-edge.mjs` | The Turso table `bin_edge` (histogram bins of `src/core/hist.js` as integer ms ranges): prints it, `--write` puts it into `server/turso/schema.sql`, `--check` exits 1 when that file is stale. Run `--write` after changing `NB`, `T0_MS` or `RATIO` (`server/README.md`, "Changing the histogram bins"). |
| `tune-gen.mjs` | Generator quality/time knobs on paired seeds: `--sizes 8,10,12 --seeds 8 --check-cap-x 0.25,0.5,1 --candidates-x 1,2 --refine-x 0,1,2 [--freed-edge | --no-freed-edge]` prints mean walls and mean ms per combination (see `generate.js` CHECK_CAP_X, PROP_CAP_X, CANDIDATES, REFINE_NODES_PER_CELL). |
| `calibrate.mjs` | Recompute the quantile cut points of the legacy grades on generated puzzles (`calibration.js`); these are calibrated to the generator, not to human ratings. |

## Targeted generation (design app: "Target difficulty generator")
`generateTargeted(n, grade, seed)` in `src/core/gen/target.js` builds a unique puzzle whose trap grade (the Play badge) is the requested grade. It is a search, not a construction: it starts from a generated unique puzzle and keeps every wall / checkpoint change that moves the trap score toward the score band of the target grade (changes that cannot lose the solution need no check; the others cost one uniqueness check).
- **Wall-minimal (the "Minimize walls" box, `o.minimize`, on by default).** The Play app's own generator keeps the candidate with the fewest walls, which is part of what makes its puzzles hard. Here every puzzle the search keeps is first stripped of each wall it can lose without getting a second solution, and the grade is read on that puzzle, so the target is the grade of a wall-minimal puzzle, not of one that is minimized afterwards into another grade. Off = the first version of the generator.
- **Retries and effort (`o.retries`, `o.effort`), no clock.** A *try* is one fresh start puzzle plus its hill-climb. `Retries` is how many tries the search may make (the CLI default is unlimited: until the target is met); it stops at the first try that meets the target, else returns the closest puzzle of all tries. `Search effort` scales how deep one try may go: at most `effort x proposalBudget(n)` changes, and it ends earlier after a quarter of that without progress. Both are counts, so the same seed + size + target + effort gives the same puzzle on every machine, and a run with more retries only adds tries after the ones a smaller run made.
- **Speed (`o.prefilter`, `o.cache`; both change the time only, the tests compare the results with them off).** Scoring a puzzle = one solver run per wrong turn (cheap) + the technique ladder's what-if count `lTr` (expensive). The ladder runs with a trial cap derived from the window of scores in which the change would be kept, and stops once the score is certain to be above it; a score that cannot reach the window even with the highest possible `lTr` is not computed either. Every score and every uniqueness verdict is remembered by puzzle (the search proposes the same puzzle again and again). Stripping the walls a puzzle does not need uses the solver's freed-edge search (is there a solution through the removed wall's edge?) and remembers, per wall that has to stay, the second solution that appears without it (its witness): the next candidate, one change away, only walks the witness path instead of searching. `r.stats` shows how often each worked. The technique ladder (`ladder.js`, the `lTr` count) keeps each what-if's segment distances per state and only re-runs the distance fields a removed edge actually cut (`incrTerritory: false` = the from-scratch reference; the tests compare both).
- **Nothing to edit when `ratings.json` changes.** The band of grade g is read from `TRAP_MODEL.cuts` and `SIZE_GRADE_CAP` at call time and the score is `trapMetrics().predicted`, so `fit-trap.mjs --write` moves the targets by itself.
- **The loop closes with the existing files:** generate at a target, rate the puzzle with the rating buttons, **Export ratings.json**, `fit-trap.mjs --write`, `target-eval.mjs`. Rate generated puzzles blind (several per grade) before trusting the numbers: the search can only follow the trap model, and it will use any weakness of it.
- Knobs live in `TARGET_CFG` (`target.js`): proposals per cell (the depth of a try), `retries` (the default number of tries), `margin`, the wall / checkpoint limits (the range the grade was fitted on). Only touch them when `target-eval.mjs` shows a grade getting unreachable.
- Cost: grades 0-3 take well under a second to a few seconds; grades 4-5 are the expensive ones (the technique ladder runs on every tried change) and grade 5 is the least reliable. `target-eval.mjs` prints the numbers on your machine, including the mean walls per cell.

## Game-of-Day seed players
`.github/workflows/gotd-seed.yml` runs `gotd-seed.mjs` every evening for the next day's puzzle in `../demo/GameOfDay/`, so the first real players already see averages and a percentile.
- `gotd-fit.mjs` maps every metric to the human 0-5 scale (`h = a + b*f(x)`, `f` = identity or log; integer grades may use the mean rating per grade) and ranks them by **skill** = 1 - leave-one-out MAE / MAE of always predicting the mean, on the rows where the metric exists (solver metrics are undefined where the reference solve was capped). A candidate is dropped when: its skill is <= .02; a `grade:*` metric's own grades are not rated in increasing order (grade 3 rated easier than grade 2); its leave-one-out predictions rank the puzzles against the ratings (Spearman <= 0); a better one comes from the same metric (`grade:B` / `B/N`) or ranks the puzzles almost identically (|Spearman| >= .95). Every dropped candidate is listed with its reason in `gotd-models.json`. `top3` / `top10` in the output = how often a candidate lands there in 200 bootstrap fits: ranks with a low `top3` are noise. Trap and ladder keep their own fits (`fit-trap.mjs`, `ladder.js`); size `n` is not a candidate (the time model handles size).
- `gotd-seed.mjs`: the first 3 defined candidates of the day play, of the next 7 the lowest and highest `h` are dropped (3..8 players). The production grade (Play badge, `trapPredicted` before it is cut into a grade) always plays: if it is not among the first 3 it takes the third place. Candidates behind the top 3 need skill >= 0.10 (`EXTRA_MIN_SKILL`; the bootstrap sd of the skill is 0.06-0.10, printed as `+-sd`). The output explains every selected name and prints the time at grade 0..5 for each. `h` -> time: `ln(median) = alpha + gamma*ln(N^2/49) + c*(h-1.5)`, a Bayesian regression over the backends' last 45 days (combined like the stats page: copies on the replicated days, sums on the others; real players only, seeds subtracted, days with >= 5 real players, `h` = the unrounded trap prediction); without data the prior in `src/core/gotd-model.js` applies (guesses, not measurements: 60 s at 7x7 / h 1.5, time ~ cells, time x2 per grade; a day only counts with >= 20 real players). Plays faster than the drawing floor, 0.5 s per cell (`FLOOR_S_PER_CELL`), are replays, not first solves: they are left out of the calibration and no seed player is faster; this applies to puzzles larger than 6x6 and to grade >= 1., and the printed `+-` shows how far the data has taken over.
- After changing `ratings.json` (and `fit-trap.mjs --write`): `node tools/gotd-fit.mjs`, commit `gotd-models.json`; `node tools/gotd-fit.mjs --check` tells whether it is stale. Real run by hand: `node tools/gotd-seed.mjs --day YYYYMMDD --token-file FILE` (FILE holds the shared secret `SEED_PLAYERS_SECRET`, see `server/README.md`; `--print-supabase-sql` prints the statement that gives each Supabase project its hash; `--only ID` seeds one backend of `src/config.js`). Dry run for a day: `npm run gotd:seed -- --day YYYYMMDD` (add `--stats cf.json` to use a saved `/stats` reply instead of fetching).

## Duplicates
The same puzzle rated twice counts twice in every fit, and a rotated / mirrored / reversed-numbering copy is the same puzzle to the solver.
- **exact** (identical puzzle): different ratings = error (exit 1, nothing written), same rating = warning and the first copy is kept.
- **equivalent** (same up to the 8 rotations/reflections of the board and reversing the numbering K..1): listed with locations, ratings and a
  picture; `--strict` makes them errors. A deliberate re-rating of the same puzzle is a useful noise check, so this is a warning by default.
- In the design app: a warning appears under the rating buttons when the puzzle you are rating is an equivalent copy of a rated one,
  and **Find duplicates** lists every group with a picture and a delete button per rating.

## After adding labels
1. Rate in the design app (range / unsure / pairwise buttons) and **Export** the files, or append puzzles to `difficulty_rate.txt`:
   `node tools/parse-ratings.mjs difficulty_rate.txt --base tools/ratings.json --out tools/ratings.json`
   (`--out` may be the base file itself; never use `>` onto it, the shell truncates it before it is read).
   **Import ratings.json** loads the repo file into a fresh browser and regrades every puzzle with the current code.
2. `node tools/check-ratings.mjs` — fix what it lists.
3. `node tools/metrics-eval.mjs` — which metric/grade is best now, and is the ladder still holding on the newest puzzles?
4. Trap grade: `node tools/fit-trap.mjs` to look, `--write` to apply, then `npm test`.
5. Ladder grade: Part 4 of `metrics-eval` shows whether `tWf` / `tTrials` in `ladder.js` `grade()` should move; change them by hand there.
6. `node tools/target-eval.mjs` (add `--independent` once in a while) — can the targeted generator still reach every grade with the refitted cuts?
7. Commit `tools/ratings.json` (and `tools/pairs.json`) together with the change.
